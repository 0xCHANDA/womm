# Proposal: WOMM v0.2 scope

Status: **proposal**. Written after the v0.1 release-candidate work;
nothing here is implemented. The owner picks the milestone; this
document ranks the candidates so the pick is informed, not novel.

## Where v0.1 stands

Linux + Node.js only. `capture` reads explicit declarations
(`engines.node`, `.nvmrc`, `packageManager`) into a deterministic
`womm.yaml`; `verify` probes `node`/`npm`/`pnpm`/`yarn` from the
system path allowlist, compares with npm's range grammar, renders a
deterministic report, exits 0/1/2/3. Hardened against hostile project
content, hostile cwd/env, hung probes and escaped descendants; fuzzed;
differential-tested against node-semver. Known usability gap:
version-managed Node under `$HOME` is not observed.

## Candidates

Scored 1–5 (5 = best) on user value, architectural fit, security
risk (5 = lowest risk), testability, effort (5 = smallest).

### 1. Version-managed Node installations (`--tool-dir`, `$HOME` shims)

See `docs/proposals/version-managers.md`. Explicit user-named
directories first, then a fixed list of shim directories, with the
executed path recorded as evidence.

| value | fit | security | testability | effort |
|---|---|---|---|---|
| 5 | 4 (one `Observation.Path` field, one report suffix) | 4 (never inherited `PATH`; refuses project paths) | 5 (fixture dirs) | 4 |

Why first: it is the single most common reason a v0.1 verify is
"truthful but useless" (`node` reported absent on a machine that runs
Node all day). It touches only L1 resolution and evidence.

### 2. Machine-readable output (`--format json`)

One stable JSON document per run: requirements, observations
(including executed path once #1 lands), statuses, reasons, summary,
exit code. Consumed by CI and by future `diff`/`explain`.

| value | fit | security | testability | effort |
|---|---|---|---|---|
| 4 | 5 (report is already presentation-only) | 5 | 5 (golden JSON, schema-versioned) | 4 |

Constraints: a `schemaVersion` field from day one; field order fixed;
no timestamps or host names (determinism); stderr diagnostics stay
on stderr.

### 3. `womm explain` / `womm diff`

`explain`: why a requirement exists (evidence chain) and why it
failed, in prose. `diff`: compare two `womm.yaml` files or a
`womm.yaml` against a captured machine snapshot.

| value | fit | security | testability | effort |
|---|---|---|---|---|
| 3 | 3 (`diff` needs a snapshot format = new schema surface) | 5 | 4 | 2 |

Why later: `explain` is mostly what the report already prints;
`diff` needs #2's data model to be worth building. Do after #2.

### 4. Go ecosystem: detector (`go.mod` `go`/`toolchain` directives) + inspector (`go version`)

Second ecosystem with the smallest semantic surface: `go.mod`'s `go`
line is a minimum version with a well-defined grammar
(`1.24`, `1.24.1`, `1.24rc1`), `toolchain` is an exact pin, and
`go version` prints one deterministic line.

| value | fit | security | testability | effort |
|---|---|---|---|---|
| 3 | 4 (new `detectors/gomod`, `inspect/gotool`; core unchanged) | 4 (`go version` executes nothing project-controlled; `GOFLAGS`/`GOTOOLCHAIN` must be forced: `GOTOOLCHAIN=local` or Go itself downloads toolchains) | 5 | 3 |

Risks to decide up front: Go's own version grammar is not semver
(`1.24` means `>=1.24.0`; `1.24rc1` orders before `1.24`); reusing
`semverrange` would be a lie. Needs its own tiny comparator, same
UNKNOWN-over-guessing rule. `GOTOOLCHAIN` is the Corepack of Go:
auto-download on `go version`? No — but on any build; the probe must
still force `GOTOOLCHAIN=local` to be safe by construction.

### 5. Services (`services:` section: PostgreSQL, Redis)

L2: TCP reachability and a version query without credentials
(PostgreSQL's startup message / `SELECT version()` needs auth;
Redis `INFO server` may too).

| value | fit | security | testability | effort |
|---|---|---|---|---|
| 3 | 2 (new L2 layer; `Observation` needs an endpoint notion) | 2 (network I/O; credentials; hostile services answering slowly) | 2 (needs containers or fakes) | 1 |

Why not v0.2: it opens network I/O and credential handling, the two
things v0.1 deliberately has none of. It also needs #2 (JSON) for
anyone to consume it in CI. Park.

### 6. Richer evidence

Record the executed path (#1), the resolved symlink target, file
hashes of the sources read, and the exact bytes of `engines.node`
already kept verbatim. Cheap once #1 exists.

| value | fit | security | testability | effort |
|---|---|---|---|---|
| 2 | 5 | 5 | 5 | 5 |

## Recommendation for v0.2

1. **#1 version-managed Node** (the usability gap), with evidence of
   the executed path.
2. **#2 `--format json`** (unlocks CI consumers and everything after).
3. **#4 Go ecosystem** only if time remains — it proves the
   architecture generalises without opening network I/O.

Explicitly not in v0.2: services (#5), `diff` (#3), Python/Docker/
Rust/Java (each larger than Go and none with a cleaner grammar than
Go's).

## Ground rules that carry over

- Every new inspector: allowlisted resolution, fixed args, sanitized
  env, cwd `/`, timeout + WaitDelay + subreaper, output cap.
- Every new comparator: explicit refusal over guessing, a differential
  corpus against the ecosystem's reference implementation.
- Every new output format: schema-versioned, deterministic, no host
  identifiers.
- One slice per PR; `docs/roadmap.md` is the plan; CHANGELOG entries
  per PR.
